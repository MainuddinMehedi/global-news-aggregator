## 1. Overview & Objective

The **Story Clustering** feature acts as the "Global Billboard" of the platform. Instead of presenting a raw, unfiltered firehose of individual news articles, it groups redundant, overlapping, or related reports from different publishers into cohesive, evolving geopolitical narratives called **Stories**.

### Why It Exists
- **Information Overload:** A major event (e.g., peace talks, a natural disaster, or geopolitical skirmishes) triggers dozens of articles from different outlets, cluttering the feed.
- **Perspective Highlight:** Grouping articles into clusters allows the frontend to contrast coverages, showing the "Perspective Gap" (e.g., state media vs. commercial media).
- **Token Efficiency:** Raw news is ingested constantly. By grouping articles locally before hitting an LLM, the system processes groups in batches, protecting against rate limits.

### Scope Boundaries
- **Dynamic Cluster Lifecycle:** Stories dynamically emerge, transition through narrative phases, and auto-archive based on impact + status + inactivity rules.
- **Frontend Top 30 Cap:** The frontend shows the top 30 active stories by a composite rank score (impact × recency × source diversity × article count × momentum). Stories beyond 30 remain active in the DB for lifecycle-appropriate retention.
- **LLM Relevant Context:** The LLM receives only the top relevant candidate stories per article batch (not the global top 30), selected by entity/region/category/text overlap scoring.

## 3. Research & Decision Matrix

### Dimensional Falsification Matrix

| Candidate Solution | Efficacy & Determinism | Operational Cost / Latency | Complexity / Debt | Outcome / Verdict |
| :--- | :--- | :--- | :--- | :--- |
| **Option A: Ingestion-Time LLM Clustering** (Clustering every article immediately using LLM) | ❌ **Low** (Highly prone to premature categorization, duplicate story creation, and context limit fatigue) | ❌ **High** (Constant API requests to LLM, high token cost) | ⚠️ **Medium** | **Disproven** (Unpredictable & costly) |
| **Option B: Pure Local TF-IDF / NLP Clustering** (Group purely using offline word similarities) | ❌ **Medium** (High speed but misses semantic nuances; hard to extract high-quality titles/summaries without LLM) |  **Low** (Completely offline, near zero cost) | ⚠️ **Medium** (Requires tweaking NLP thresholds constantly) | **Disproven** (Fails to create high-quality readable summaries) |
| **Option C: Decoupled Entity-Matching + LLM Batching** (Deterministic local entity filtering first, followed by batch LLM decisions) |  **High** (Entity matching groups candidate articles locally. LLM only performs final categorization and summaries) |  **Medium** (LLM is called in batches only when critical mass is met; rate limits are respected) |  **Low** (Clean separation of concerns, stable) | **Accepted** (Current Implementation) |

## 4. Technical Architecture & Data Model

To prevent API rate limits, network crashes, and LLM amnesia, the system uses a **Decoupled Architecture**: Ingestion and Clustering run as asynchronous, independent processes.

### Data Model (Prisma Schema)

_Current as of Phase 1. See [schema.prisma](file:///home/mainu/programming/projects/automation/geopolitical-news-monitor/global-news-aggregator/prisma/schema.prisma) for the authoritative definition._

```prisma
model ProcessedArticle {
  id             String         @id @default(uuid())
  rawArticleId   String         @unique
  rawArticle     RawArticle     @relation(fields: [rawArticleId], references: [id], onDelete: Cascade)
  categories     Category[]     @relation("ProcessedArticleCategories")
  entities       String[]
  sentimentScore Float?
  eventRegion    String?
  clusterStatus  String         @default("HOLDING") // HOLDING | CLUSTERED | ARCHIVED_UNCLUSTERED
  clusteredAt    DateTime?
  storyClusters  StoryCluster[] @relation("ArticleStoryClusters")
}

model StoryCluster {
  id               String   @id @default(uuid())
  slug             String   @unique
  title            String
  summary          String   @db.Text
  timeWindow       String?
  keyDevelopments  Json?
  isActive         Boolean  @default(true)
  impact           String?  // CRITICAL | HIGH | MEDIUM | LOW
  impactScore      Float?
  status           String?  @default("DEVELOPING") // EMERGING | DEVELOPING | ESCALATING | SLOW_BURN | STABLE | RESOLVING | ARCHIVED
  momentumScore    Float    @default(0)
  whyItMatters     String?  @db.Text
  regions          String[]
  themes           String[]
  articleCount     Int      @default(0)
  sourceCount      Int?
  topSources       String[]
  lastActivityAt   DateTime?
  activityScore    Float?
  trendData        Json?
  createdAt        DateTime @default(now())
  updatedAt        DateTime @updatedAt
  articles         ProcessedArticle[] @relation("ArticleStoryClusters")
}
```

### Process Flow
1. **Ingestion & Holding Tank:** `npm run ingest` crawls new articles, runs AI enrichment (entity extraction, categorization, sentiment), and writes them as `HOLDING`.
2. **Lifecycle Check:** The worker (`npm run cluster`) first applies lifecycle rules — active stories that have exceeded their inactivity window (based on impact × status) are deactivated.
3. **Holding Window Check:** `HOLDING` articles within the configurable accumulation window (default 168h, env `CLUSTER_HOLDING_WINDOW_HOURS`) are fetched. Older articles are silently archived as `ARCHIVED_UNCLUSTERED`.
4. **Entity Overlap Detection:** Articles are grouped using connected-components grouping. Two articles overlap if they share at least **2 normalized entities** (env `CLUSTER_MIN_ENTITY_OVERLAP`). Normalization includes lowercase, punctuation cleanup, alias mapping (`U.S.` → `United States`), and title prefix stripping (`President Putin` → `Putin`). Original entity strings are preserved.
5. **Critical Mass Check:** Groups with at least **3 articles** (env `CLUSTER_MIN_GROUP_SIZE`) proceed. Others remain in `HOLDING` until they expire.
6. **Token-Safe Chunking:** Grouped articles are sliced into batches of 5.
7. **Relevant Candidate Selection:** For each batch, the top 30 most relevant active stories (env `CLUSTER_LLM_CANDIDATE_LIMIT`) are selected using a local relevance score — entity overlap × region match × category/theme match × text similarity × recency compatibility × rank score. This replaces the old global Top 30 approach.
8. **LLM Categorization:** Groq (or configured fallback model) receives the batch articles + relevant candidate stories. It decides assignment, new cluster creation, or unclustered status. Allowed statuses: `EMERGING`, `DEVELOPING`, `ESCALATING`, `SLOW_BURN`, `STABLE`, `RESOLVING`, `ARCHIVED`.
9. **Database Write & Revalidation:** Results are persisted — new clusters are created with sanitized metadata, existing clusters are updated with merged developments, momentum is incremented for new assignments. Unassigned articles are marked `ARCHIVED_UNCLUSTERED`. Momentum decays globally by 0.5 per run (ranking signal only, does not archive). Then `revalidateCache` refreshes the frontend.

```mermaid
graph TD
    A[RSS Feeds Ingestion] -->|AI Enrichment| B[ProcessedArticle: HOLDING]
    B -->|Lifecycle Check| L{Deactivate Stale?}
    L -->|Impact+Status+Inactivity| M[Deactivate Story]
    B -->|Holding Window Pass| N{Within Window?}
    N -->|No (>168h default)| O[ARCHIVED_UNCLUSTERED]
    N -->|Yes| C{Critical Mass?}
    C -->|Entity Overlap >=2 & Group >=3| E[Batch into Chunks of 5]
    C -->|No| D[Stay in HOLDING]
    E -->|Relevant Candidate Selection| F[Groq AI Decision]
    F -->|Assign / Create Story| G[StoryCluster Updated]
    G -->|Momentum Decay + Revalidation| H[Next.js Frontend Refreshed]
```

## 6. Future Roadmap & "Remember It" Notes

### Phase 1 (implemented)
- ✅ Momentum no longer archives stories — lifecycle (impact + status + inactivity) is the single source of truth for archival.
- ✅ Connected-components grouping replaces anchor-centric entity overlap.
- ✅ Relevant top 30 candidate stories replace global top 30 LLM context.
- ✅ Configurable holding window (default 168h) for slow-burn accumulation.
- ✅ Conservative entity normalization (alias dictionary, title stripping, lowercase, punctuation cleanup).
- ✅ Expanded statuses: `EMERGING`, `DEVELOPING`, `ESCALATING`, `SLOW_BURN`, `STABLE`, `RESOLVING`, `ARCHIVED`.
- ✅ Sanitized new-cluster metadata before DB writes.
- ✅ Frontend ranking by composite score (impact × recency × source diversity × article count × momentum).

### Phase 2 (planned)
See the full Phase 2 roadmap in [Story clustering implementation plan - solving current problems](Story%20clustering%20implementation%20plan%20-%20solving%20current%20problems.md) section 10. Key items:
- Hidden candidate stories (single-article detection with candidate-to-story promotion).
- Article-level `themes` for better candidate scoring.
- Post-run duplicate detection (logging-only first).
- LLM canonical entity prompting + entity match logging.
- Lifecycle tuning based on observed story behavior.

### Longer-term
- **Embeddings + Vector DB:** Convert ingested articles to vectors using Gemini Embeddings and store them in Supabase `pgvector`. Use cosine similarity for article-to-article groups and article-to-story mappings. Use the LLM *exclusively* to write, update, and summarize cluster metadata — drastically reducing token usage.
- **`storyType` field:** Cleaner model with `BREAKING`, `SLOW_BURN`, `INVESTIGATIVE_FALLOUT`, `CONTEXT` types separated from status (narrative phase). Deferred until real cluster behavior proves the need.
- **Graph database:** Consider when relationship traversal becomes a core product feature.
- **Model Alignment:**
  - Standard prompt generation relies on models registered in [[docs/AI_MODELS|AI_MODELS.md]]. If migrating tasks to Google AI Studio, utilize `gemini-2.5-flash` or `gemini-3.1-flash-lite` instead of obsolete Gemini 1.5 variants.
