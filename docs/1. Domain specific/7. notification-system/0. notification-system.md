# Notification System — Intent & Design

## Scope

A global in-app notification system that covers the entire application, including (but not limited to):

- New feed sources seeded/added (broadcast to all users)
- Future: article alerts, story cluster updates, system announcements

## Triggers (Known)

| Trigger | Audience | Schedule |
|---------|----------|----------|
| Feed sources seeded via admin | All users | Immediate (or digest — TBD) |
| New feed source added via admin CRUD | All users | Immediate (or digest — TBD) |

## Delivery Channels

| Channel | Status | Configurable |
|---------|--------|-------------|
| In-app (bell icon in Navbar) | Placeholder exists, needs wiring | Yes — Settings → Notifications |
| Discord webhook | Locked Topics only, needs extension | Yes — Settings → Notifications |
| Telegram | Locked Topics only, needs extension | Yes — Settings → Notifications |

## Schedule

Whether notifications are delivered immediately or batched into a digest (e.g., weekly "3 new sources added") is **TBD**. This should be configurable per user in Settings → Notifications.

## Broadcast Model

When an admin performs an action that triggers a notification (seed feeds, add source):

1. A notification record is created in the database (new `AppNotification` model or similar)
2. All active users receive an in-app notification (bell icon badge increments)
3. Users with Discord/Telegram channels configured also receive external delivery

## Data Model (Not Implemented)

A new model will be needed, likely:

```
model AppNotification {
  id        String   @id @default(uuid())
  userId    String   // target user (or null for broadcast)
  type      String   // "feed_seeded", "source_added", etc.
  title     String
  body      String?
  link      String?  // deep link to relevant admin page
  isRead    Boolean  @default(false)
  createdAt DateTime @default(now())
}
```

Or a broadcast model for system-wide announcements with read tracking.
